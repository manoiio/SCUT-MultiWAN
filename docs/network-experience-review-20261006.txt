范围与基线

本轮是审查与只读诊断，没有修改生产脚本、配置、认证、会话、预算、
路由、无线速率或服务，没有运行扫描/部署/回滚，没有提交或推送。
开始时 main 与 origin/main 一致，工作树干净，HEAD 为 bb5a178。
审阅 README、OPERATIONS、candidate 中的维护/Portal/日历/有线脚本、
有线源码适配器/构建器及隔离测试。以下是优化建议，尚未实现或部署。

生产证据

01:19 起只读检查观察到：
* Native 与 USB 关联同一 BSSID、同一 5180 MHz 信道；Native TX MCS9、
  RX MCS11，USB TX/RX MCS11。此时不是原生 6 Mbps 故障状态。
* 有线保持原认证引擎 PID/starttime；日志持续出现同会话 Identity 挑战
  和完成的 UDP 心跳，未主动重启或注销。
* 三路绑定接口的百度 HTTPS HEAD 均为 200，总时间分别约
  Native 85.6 ms、USB 77.8 ms、有线 85.8 ms。只是当前短时验证，
  未测满载延迟、Internet 吞吐、真实故障、长期漫游或停止恢复。
* 表 103 三路权重 1:1:1，pref 103 为 iif br-lan，连接哈希为 1，
  all.rp_filter 为 0。有线协商 100 Mbps/full，错误计数检查为 0；
  100 Mbps 是物理协商值，不能当作 Internet 测速。
* 六个关键文本目标的 SHA256 与本地 candidate 相同：速率控制、
  ECMP、common、wired-run、scut-wired init、scut-wired-gate。
  已安装有线程序哈希仍与此前最终版本一致。
* curl 使用系统解析器，没有列出 c-ares；/etc/resolv.conf 指向本地
  DNS，自动上游名单混合无线/有线 DNS。路由器普通 IPv4 本地请求的
  main 出口是 Native，不经过 iif br-lan 规则。
* wan6 有 IPv6 地址及源地址限定默认路由；本轮未验证公网 IPv6、
  LAN 前缀发布或客户端是否实际使用它。IPv4 三路检查不涵盖这些。
* tc 未安装，所检查的 sqm-scripts/luci-app-sqm/kmod-sched-cake 未报告
  安装。未读取所有内核队列，不能据此断言设备完全没有排队管理。

优先修复的问题

1. [P1] 有线同会话挑战遇到 Portal 锁占用即退出

位置：tools/wired-main.c:37-48；tools/build_wired_client.py 的
IDENTITY/MD5 替换逻辑；candidate/usr/bin/dualwan-refresh:65-67。

wired_renew 用 LOCK_NB 获取锁，失败返回 75；适配后的 Handler 把
renew 的非零结果返回为 76；Authentication 把 Handler 的非零结果
作为退出条件。dualwan-refresh 持有同一个 Portal 锁进行逐路 HTTPS
探测，Native 切换也可能长时间持锁。服务器挑战到达的时机与这些
维护操作重合，就可能让仍在线的有线引擎退出。

现有协议测试明确覆盖了 renew 返回 75/76 时不发送并返回 76，
但没有把它当作“在线会话应继续等待”的可用性问题。此轮没有故意
占用生产锁来制造断线；这是确定的代码退出路径，不是已复现的断网。

建议：同会话挑战采用有界待处理状态，在协议事件循环继续接收 UDP，
锁可用后再在真实全局锁下回复；超过经验证的服务器响应期限才退出。
不能绕过 Portal 锁，也不能发送新的 EAPOL Start。健康探测可研究
移到锁外，最终路由提交在锁内重新核对接口/IP/关联/引擎身份及会话
快照，防止使用已变化的认证拓扑。两项应一起设计并验证。

2. [P2] 区分正常停网与假日保护期的已有会话行为

位置：candidate/usr/bin/scut-wired-gate:50-54；common.sh:75-83。

用户在本轮进一步明确：工作日/补班日学校 00:07–06:30 会断网，
认证掉线是正常现象，只需在 07:00 后重新认证。这是当前审查依据；
不将工作夜退出列为缺陷，也不建议在该时段回复挑战/重新认证以保网。
现有 00:06–07:00 静默包含前后缓冲，不因学校时间说明自动缩短。

challenge 调用 mw_require_active 60，所以假日 00:06–00:25 同样拒绝
已有会话挑战；与上一项退出路径结合，可能丢掉假日仍可用的连接。
该项仅在假日保护期原本应保留可用连接时有优化价值。00:05:00 起
的边界余量也会拒绝，但工作夜学校即将停网时不应视为异常。

本轮在实际 BusyBox ash 中只调用 common 辅助函数，用虚拟时钟及
日期判断核对，无网络、无线或文件写入：
* 假日 00:04:59：active(60)=0，route(60)=0。
* 假日 00:05:00：active(60)=76，route(60)=76。
* 假日 00:10:00：active(60)=76，route(60)=0。
* 假日 00:25:00：两者均为 0。
* 工作日 01:00:00：两者均为 76；07:00:00 均为 0。

如优化假日保活，应定义只作用于允许供网日期的既有会话权限，保留
真实锁、会话/服务器身份和有效记录；不允许新 Start、新登录、无限
重试或额度绕过。工作日/补班日/未知年度夜间继续拒绝，07:00 后恢复。
不能直接将 challenge 改用 route 守卫就认为全部语义正确；还需测试
假日保护期与工作夜的区别。目前 wired-cases.sh 断言假日保护期
challenge 返回 76，应按所需假日行为重新评估，工作夜拒绝断言保留。

07:00 有线恢复也需关注：当前没有专门的 07:00 有线 cron，而是
procd 每 60 秒重新启动 wrapper，过 07:00 后 active 守卫放行、夜间
两次额度/阻断不再限制 claim。因重试相位、Portal 锁和协议过程，
不能保证恰好 07:00:00 在线。需观察普通工作夜实际掉线到晨间恢复，
覆盖旧会话确认释放、额度耗尽、锁占用和恢复后 HTTPS/入表；必要时
改为明确的 07:00 唤醒并有界等待，不能并行制造第二个有线引擎。

3. [P1] 白天健康判断只有一个站点，DNS 还存在共同依赖

位置：candidate/usr/lib/scut-multiwan/common.sh:160-178。

白天 mw_online 只检查百度；只有夜间才检查淘宝备用目标。
online_confirm 的第二次尝试仍然是同一个目标。目标站/TLS/解析故障
可能让健康链路被剔除，三路共同探测失败则移除策略。Portal 入口
仍要求精确校园重定向，所以这不等于会盲目认证，但路由体验会受影响。

实际 BusyBox 只读函数 mock：百度失败、淘宝成功时，白天返回 1，
假日夜间返回 0。此次是函数行为核对，没有阻断真实站点。

curl 官方说明 --interface 不影响 DNS；本机系统 DNS 上游请求不受
iif br-lan 三路规则控制。即使绑定有线 HTTPS，其域名解析也不是
独立的有线健康证据。DNS 故障可能放大成多路共同失败。

建议：全天主目标失败再尝试独立 HTTPS 目标，成功仍须合法 TLS 和
HTTP 200；设置总探测时间预算，保留“普通超时不触发登录”。记录
解析失败、连接失败、TLS 失败、非 200、Portal 重定向的分类结果。
接口独立解析须按当前 curl 功能选择实现，不能直接使用要求 c-ares
的 --dns-interface。可研究每链路 DNS 查询与短期有时效的解析缓存，
使用 --resolve 时保持域名/SNI/证书验证，不能永久固定 CDN IP 或
把单个公网 IP ping 当作认证在线证据。

4. [P2] 路由恢复缺少跨轮稳定要求，容易随短暂成功反复加入/移除

位置：candidate/usr/bin/dualwan-refresh:30-35、74-96、122-125。

当前剔除前同轮复核一次，恢复却一次 HTTPS 200 就立即加入，没有
跨轮状态/恢复冷却；默认和直连路由即使拓扑相同也每轮 replace。
有线每次挑战完成后又触发全路探测/刷新，本轮日志约每分钟发生。

建议：carrier/关联/可信引擎身份丢失立即剔除；软失败使用有总时限
的独立站点复核；恢复要求连续成功并设置短保持期。保持三路健康
1:1:1、双无线健康 1:1 和 iif br-lan。拓扑未变可跳过路由改写，
探测不必跳过；引擎首次 ready/真实退出仍须请求及时刷新。

ECMP 增删下一跳可能改变部分既有连接的路径，连接哈希并不等于
连接永远绑定一个出口。因此减少误剔除/立即重加有体验价值。
相同拓扑的 replace 没有在本轮证明会造成断线，不应宣称每分钟
刷新就是已知故障原因。若要进一步稳定已有连接，需单独评估
conntrack/出口绑定等更大改动，不能顺带改现有策略。

MCS 控制器优化

位置：candidate/usr/bin/fix-qca-sta-rate；生产 Native cron 白天 5 分钟。

已实现的行为是：
* 当前 TX >9 先压到 MCS9；无可信当前/历史目标时保守初始化 MCS7。
* MCS9 的 delta failed >=20 且 failed*10 >=delta packets 时降档；
  新从 MCS11 压到 MCS9 的一轮不使用先前 failure 惩罚 MCS9。
* RX 中位数 <9，或 5 次网关探测至多 3 次成功时降到 MCS7。
* MCS7 时 RX >=9、至少 4/5 网关成功、无严重 failure，GOOD_SINCE
  跨满 300 秒后升 MCS9；升档后另做 5 次网关/失败数验证，失败回退。
* 新关联前 15 秒不凭 RX 降档/升档；phy3 被排除；静默不维护速率。

主要改进点：

A. [P2] “立即降档”目前是下一轮检查时立即，白天故障可能等待近
5 分钟；“连续良好 300 秒”只由两轮短采样支持，不能观察中间状态。
建议把白天轻量速率维护与完整 watchdog/扫描分离，试验 30–60 秒
采样；全扫描继续低频并严格禁夜间扫描。选 30 秒时，升档要求连续
合格观测跨满 300 秒，采样间隔越界/关联变化/计数器复位即重置，
不能单纯缩短 300 秒，或提高 watchdog 频率而连带增加全扫描/认证。

B. [P2] RX 被当作直接 TX 降档依据，且缺少有效样本数门槛。
RX 反映 AP 发往 STA 的当前速率，TX 是另一方向。现在哪怕 5 轮只有
一个有效 RX=8，其“中位数”仍为 8，会把 MCS9 降到 MCS7；4 个缺失
样本没有降低结论可信度。小 ICMP 包产生的 RX 也不等于持续下载质量。
建议 RX-only 低值先要求足够的新鲜有效样本和连续短窗口；严重 TX
失败或可靠的链路丢包仍快速降档。少量/缺失样本保持档位但禁止升档。
仅接受合法 HE MCS 范围，并核对关联/NSS/带宽是否可比。阈值需通过
mock 和自然运行数据验证，不把所有 RX0 都当初始化，也不取消宽限。

C. [P2] 网关 5 个 ICMP 样本没有 RTT 统计，服务器限速/拥塞也可能
导致丢包，降 TX MCS 不一定有效。建议同时记录成功率、RTT 中位数/
尾部变化和实际 TX failure，区分无线恶化与网关/公网故障。
tx_failed 是 MPDU，tx_packets 是 MSDU/MMPDU，按两者做的比例是
启发式指标，不能标成精确“10% 空口丢包”。当前 Native tx_retries
报告为 0，未经驱动有效性验证不能拿它做可靠升档依据。

D. [P2] 采样过程没有最终关联身份复核；BSSID/频率在采样中变化时，
可能应用旧判断并把新关联计数写到旧 LINK_KEY。建议读 assoc_at 或
其他可验证关联标识，应用前与保存前复核；同 BSSID 重关联也必须
重置观测窗口。promotion 验证应包含 TX 流量量级及失效率的背景，
失败后增加冷却，避免在边缘链路每隔几分钟反复尝试 MCS9。

本轮日志显示 Native 长时间保持 MCS9；22:55 和 23:55 RX 在 8/9
附近摆动时中位数仍为 9，没有在该记录中证明发生 MCS7/MCS9 振荡。
MCS 优化的预期是降低故障反应时间与误判，不能承诺 Internet 峰值
速度提高；QCA 上限仍为 MCS9，不因强 RSSI 自动开放 MCS11。

其他与体验相关的改进

5. [P2] Native 最终切换失败缺少完整事务恢复。
make_primary 在候选已认证后 ifdown/ifup DHCP，可能改变 IP 或再次
中断数据面；最终 wait_internet 失败仅告警返回，此时旧 radio 已关闭，
并不进入前面的 rollback_old。现有 mock 给每个接口固定 IP，未覆盖
这次 DHCP 变化。优先研究无需拆掉 DHCP 即更新 metric 的安全方案；
否则最终失败需纳入事务恢复，先确认释放候选，再关联/恢复旧路径，
释放不确定仍须停止后续认证。不能复用当前 rollback_old 就假定完备。

6. [P2] RSSI 优选及失败重试应更重视实际收益。
6 dB 滞回避免小幅切换，但强信号不等于低拥塞/高吞吐。失败扫描的
retry_scan 每 5 分钟再次触发，可能持续打断流量。建议失败原因分类
加有界退避；弱信号事件结合公网/网关质量及现有流量，防止只为更强
RSSI 重复切换。保留 07:00 强制检查及会话安全；不固定 BSSID。

7. [P2] 以满载延迟补足性能证据，而后决定 SQM。
目前只有空载/轻载 HTTPS 和物理速率，没有“下载/上传时视频、游戏、
网页是否卡顿”的排队数据。下一轮应在受控的低影响测试中逐链路记录
空载与负载下公网 RTT、丢包、上传/下载吞吐及 CPU。若确认排队膨胀，
再试 CAKE/fq_codel/SQM；整形值按实际瓶颈测量，不能直接按 100 Mbps
端口或 Wi-Fi 458.8/573.5 Mbps 标称值设置。三路须分别评估，共享 AP
不能当作两个独立的稳定容量。任何测试性配置需要备份与独立回滚。

8. [P2] IPv6 和路由器本地请求是独立的诊断范围。
脚本全部公网检测用 -4；三路 IPv4 健康不能证明客户端 IPv6 健康。
本地 DNS/路由器上的代理连接也不匹配 iif br-lan，不能通过改成 LAN
源地址规则来解决。先核对客户端是否实际用 IPv6、代理在哪里终结，
再决定独立 IPv6 监测/本地流量策略；不据现有 IPv6 地址直接禁 IPv6。

9. [P3] 状态页/日志和服务停止可改进。
dualwan-refresh status 的有线 online 只查 HTTPS，不要求应用路径的
引擎身份，可产生“status online 但未纳入路由”的误解。night-control
status 只列 Native/USB 预算，缺少 wired 额度/阻断状态。建议统一显示
物理/关联、IP、引擎/心跳、HTTPS、预算、入表及最后原因，避免把不同
状态都称在线。只记录处理过的原因和计数，不记录原始报文或凭据。

SIGTERM 当前 _exit，跳过正常注销/ready 撤回/引擎自己的路由刷新；
包装器会刷新且 PID 检查会拒绝死进程，持久会话也能保护下次启动，
所以不能说已存在无保护的盲目重登。但应通过信号置位和正常循环退出
使停止更可预期，并测试锁占用/静默/释放不确定时的结果。异步 route
子进程还继承引擎 singleton FD，应在 exec 前关闭无关 FD，避免主引擎
退出后辅助进程继续持有 singleton。协议超时建议用单调时钟，防 NTP
调整影响等待/保活；日历和跨重启认证额度仍使用受校验的墙上时钟。

验证计划

本轮只进行了代码审查、生产只读快照和 common 辅助函数的虚拟时钟/
HTTPS mock；没有重新执行完整 100 组套件或 14 项协议测试，既有
通过记录仍是历史证据。本轮未运行生成的 run.sh，也未主动制造真实
断网、锁竞争、午夜挑战或新关联。

实施顺序建议：
1) 有线 challenge 的锁等待；核对普通工作夜 07:00 恢复、仅允许日期
   的保活权限。补事件循环与锁并发集成测试，保持工作夜静默。
2) 全日备用 HTTPS、DNS 分类及路由恢复滞回，覆盖目标故障、共享 DNS
   故障、PID/关联在探测途中变化，以及所有健康组合。
3) 独立轻量 MCS 采样，覆盖稀疏 RX、RX/TX 不对称、计数器/关联重置、
   采样遗漏、快速 failure、promotion 回退及夜间无速率改动。
4) Native 最终 DHCP/切换事务失败，再做性能观测、SQM 和 IPv6 决策。

新实现须在 OpenWrt/Linux BusyBox ash 的隔离目录运行回归，有线
适配器另做无真实 socket 的协议/事件循环测试。通过后才能准备新的
专用备份、原子部署、回滚和自然运行观察；不重跑历史安装器，不删除
会话/预算，不重置配置，不顺带改变三路权重或现有静默规则。
