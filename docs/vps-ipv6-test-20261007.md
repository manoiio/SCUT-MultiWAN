# 校园三路 IPv6 与新 VPS 验证（2026-10-07）

测试于 GMT+8 14:10–14:53 完成。用户要求生产出口仍为新 VPS；香港仅作诊断接收端。用户先追加 5GB、再追加 10GB，累计额度由 13GB 增至 28GB。本轮没有替换生产代理或更改其出口。

## 实测结论

两路校园无线可以取得公网 IPv6，绑定各自地址访问公网 HTTPS 均返回 200。有线原有 IPv6 同样可用。新 VPS 三路 IPv6 的整体速度约 55–58Mbps，低于既有 IPv4 代理；更换拥塞控制、设置 FQ60Mbps 及更换 IPv6 地址后缀，都没有明显改善。

所有 MPTCP 接收样本均完整检查字节数、固定数据模式及 SHA-256。256MiB 校验值为 `486cc817b95d853d3c357ff283b204c0144bd255e73fe2deb1389493b257e3c0`。新 VPS 三路连接通过 Linux `ss -Mni` 的 `subflows_total:3` 确認，未退化成普通 TCP。BBR 样本也通过各 TCP 子流状态确认算法实际生效。

双地址并发时，原地址 28.72Mbps、新地址 29.69Mbps，两次请求起始仅差约 0.1ms；原地址首包有约 1.17 秒延迟，新地址约 0.09 秒。按最早开始至最晚完成的共同时间 37.3839 秒计算合计 57.44Mbps，没有将两条不同时间窗的平均值直接相加。两个连接分别为单子流，并使用不同的服务器本地 IPv6 与校园源 IPv6。

另有三条各 64MiB 的单子流并发测试，分别约 21.16 / 22.11 / 27.58Mbps；启动存在数秒错开，因此不能把三个全程平均值相加当作聚合速度。一次队列修改过程中的接收样本中断，整个样本排除性能对照，但网卡流量仍计入额度。

以上证据支持“新 VPS 的 IPv6 上游或路径存在共同约 60Mbps 瓶颈”，不能确定是卖家整形、物理线路容量还是运营商路径拥塞，也不能据此确认校园网对每个长连接固定限速 50Mbps。香港与新 VPS 的链路、RTT、系统内核不同；香港样本是路径对照，未证明长期 132Mbps，更没有达到 300Mbps。没有在本轮重新下载 115 文件。

## IPv6 能否改变

新 VPS 原有 IPv6 为 `2409:8a55:727a:5740:be24:11ff:fea4:ae10/64`，默认网关为 `fe80::ea1c:baff:fe8e:6ff2`，PMTU 1492。本轮在 ens18 增加同 /64 临时地址 `2409:8a55:727a:5740:5b7e:14c9:8a3f:2707`，DAD 通过；绑定该地址访问公网成功，外部也成功连接该地址的 TLS/MPTCP 测试服务。

因此，同一前缀内的地址后缀可以改变，本机已经实测成功。但它仍使用原网关与上游；单独换后缀没有改变线路，也没有提升本轮速度。两个地址同时传输仍合计约 57Mbps，进一步排除了“只针对原地址限速，换后缀即可加速”的简单解释。

只读检查面板 VM 298：当前运营商选择仍是联通专线，可见五个运营商按钮，没有单独的 IPv6 线路或前缀设置入口。本轮没有切换面板线路。面板选择、VM 的 IPv4 出口与 IPv6 上游是不同的观察对象；要使用不同的 IPv6 上游，需要宿主侧提供对应的可路由前缀和网关或其他明确的路由能力，不能自行填入其他运营商前缀后就宣称可用。

## 临时变更与清理

无线使用 netifd 动态 DHCPv6 接口 `scut_native6_test` / `scut_usb6_test`，分别绑定 phy2-sta0 / phy3-sta0；不请求 PD，不改 DNS，不替换主 IPv6 默认路由。临时源路由表为 206 / 207，手工规则优先级 86 / 87，测试 MPTCP 端点为 207 / 208。没有写 UCI、重启无线、进行 DHCPv4 恢复或校园认证/注销。

新 VPS 临时 TLS/MPTCP 端口为 57502，路由器测试入口为 1089，双地址并发另用 1090；香港临时服务使用原先空闲的 IPv6 TCP80。测试服务有字节、并发和运行时限。新 VPS 的测试队列仅匹配 IPv6 TCP 源端口 57502；生产 IPv4 TCP57501 的 FQ50 保持。BBR 只设置在测试套接字，VPS 全局仍为 CUBIC。

14:52–14:53 已完成清理：停止全部临时测试服务，删除新 VPS 的临时 IPv6、IPv6 队列过滤器，恢复原先 1:2 下的 fq_codel，卸载本轮额外加载的 BBR 模块。路由器移除动态无线 IPv6、临时规则/表/端点；netifd 异步清理完成后，只剩原有有线 IPv6、主路由和原 IPv4 MPTCP 端点 202 / 203。测试私有配置、香港临时密钥和测试二进制均已删除。路由器备份 `/root/scut-ipv6-backup-20261007` 保留，清理守卫已取消。

最终验证：生产入口 `192.168.1.1:1088` HTTPS HEAD 返回 200；新 VPS 服务 enabled / active；两端生产二进制 SHA 与测试前一致；网络、无线、防火墙、DHCP 以及三个校园会话文件共七项 SHA 检查全部通过；IPv4 表 103 仍为 iif br-lan、三路 1:1:1，限缩的 IPv4 源/目标策略仍为 80–82。无线 IPv6 此次仅临时开启验证，没有持久部署。

本地 Go 源码新增可选 `transport_network`（默认 tcp4，可选择 tcp6）及 `congestion_control`（默认沿用系统，可选 cubic/bbr），用于本轮隔离服务。Go race 回归通过，Linux 两架构已构建并实测。源码更新没有替换现有生产二进制；LAN 监听及 CDN 上游仍保持原有 IPv4 行为。

联通方向 45 秒共同窗口实测约 142.6Mbps，确实与“所有相关包都通过同一条硬上限 100Mbps 上传链路”不相容。向香港 1GiB 样本后段却约 95–99Mbps；仍可能涉及流级/目的地策略、较大突发额度、共享上游或内部转发，不能据此确认专线升级。生产代理另有主动设置的每子流 FQ50，三路约 150Mbps 上限，因此生产代理约 140Mbps 也不能用作 VPS 最大上传能力测量。所有提到的 60/140Mbps 均为有效载荷接收速度，不是 Mb/s 与 MB/s 混用。
