## 三路合计约 300 Mbps 时应关注什么

300 Mbps 约为 37.5 MB/s。按 1500 字节 IP 包粗算约 25000 个下行包/秒，另外有 ACK 和其他业务；小包负载会显著提高包率。转发使用有限缓冲，不缓存整个下载内容，因此无法按“下载速率×持续时间”推算路由器 RAM 占用。

四核/当前闲置情况不能证明 300 Mbps 稳定：一核软中断可能先满，USB 收发和无线驱动分配可能成为瓶颈；总平均 CPU 会掩盖单核问题。两个无线连接同 AP/信道，其容量不是独立相加。1:1:1 按连接哈希分担，不保证带宽恰好各三分之一；有线接近物理上限时可能先排队。若校园有线只提供百兆，把端口改千兆也不会自动增加公网限速。

应由千兆 LAN 客户端进行多连接 IPv4 下载，绕过代理，确认三路接口实际承载的字节差分。路由器自身下载不经过 iif br-lan，且引入本机 TLS 开销，不能替代转发测试。单个下载连接无法覆盖三路；测速源能力不足或出口分布失衡也不能判定路由器不足。

建议测试分两轮，尚未执行：

1. 低影响短测：空载基线 30 秒，约 100/200/270–300 Mbps 各 20–30 秒，再观察恢复 30 秒。同步每 2–5 秒读取每核 CPU、MemAvailable/Slab/AnonPages、接口吞吐/错误/丢弃、softnet 差分、有线进程身份；比较网关和公网 RTT/HTTPS 延迟。
2. 第一轮正常后，在可接受占用带宽的时段连续 10–15 分钟接近目标负载。300 Mbps 持续 10 分钟约产生 22.5 GB 流量，应按使用场景安排；短测不能排除无线缓冲增长或长期故障。

观测至少区分：达不到吞吐但 CPU 不高（源/校园限速/共享 AP）；单核/软中断饱和（转发数据路径）；吞吐足够但时延显著升高（排队）；MemAvailable 持续下降且不恢复（驱动/缓冲容量）。经验性的暂停线可设 MemAvailable<32 MiB 或连续公网验证失败，停止的仅是测试流量，不自动重启、认证、清会话或刷缓存。32 MiB 是测试保护建议，不是已证实的 OOM 临界值。

## 内存是否应提升

不建议现在通过改 DTS/启动参数回收硬件保留区。启动日志明确有 wcnss 95 MiB、NSS 16 MiB，以及安全固件/引导相关保留区；它们不属于可随意释放的文件缓存。MemTotal 少于物理 RAM 不证明内存泄漏。

不建议定时 drop_caches、自动低内存重启或在闪存建立 swap。它们不能修复无线驱动缓冲问题，并可能损害访问延迟/连接连续性。当前用户匿名页仅约 6 MiB，预期 zram 收益有限；zram 不增加物理 RAM，也不能直接换出无线固件/DMA等不可交换内存。本轮没有安装或启用 zram。

**需要保留的负载风险：** OpenWrt 上游 issue #24154 的报告者在同款 MX4200 V1、25.12.4 与 mac80211-backports 6.18.26 上观察到持续流量下 ath11k RX 缓冲过大导致内存耗尽。当前为 25.12.5、相同 backports 版本；这使该报告与本机相关，但不能据此断言本机已经发生或一定会发生。报告中的缩小 ring 方案是第三方实验，当前设备是否包含等价修订未核对；本轮未应用补丁、重载无线或刷机。[上游报告](https://github.com/openwrt/openwrt/issues/24154)、[报告者的实验补丁与限制](https://github.com/enspect/ath11k-ipq807x-rx-buffer-oom-fix)。

若持续 300 Mbps 测试确认内存余量不足，优先辨别驱动缓冲与可交换用户页，评估对应驱动修订。若不接受固件实验且经常持续高流量/多客户端，才考虑更多 RAM 的设备；若证据是单核瓶颈，需要更强转发性能，单加 RAM 不能解决。

## 调整优先级

1. 首先做符合实际 LAN 路径的持续负载与延迟测试；当前不改三路权重/静默/会话保护。
2. 若 CPU/软中断饱和，比较软件 flow offloading 的受控开关测试，核对故障链路移出后的旧连接/新连接行为。flowtable 缓存会绕过常规转发路径，出口变化可能留下过期条目，不可直接认定与当前动态 ECMP 完全兼容；安装 qca_nss_dp 不等于启用 NSS 硬件 NAT。[Linux 6.12 flowtable 文档](https://docs.kernel.org/6.12/networking/nf_flowtable.html)。
3. 若主要问题是满载延迟，才比较 SQM/fq_codel/CAKE；按各路实测瓶颈设置，不盲设总口 300 Mbps，不先装三路重整形增加 CPU 工作。共享 AP 与可变无线容量需单独考虑。[OpenWrt SQM 说明](https://openwrt.org/docs/guide-user/network/traffic-shaping/sqm)。
4. Portal 响应容量上限、部署后确认清理暂存属于小幅防御性改进；本轮提出建议，未修改实现或部署。

本轮没有对脚本做功能改动，因此没有重跑隔离/协议 mock；历史 113/19 通过不构成 300 Mbps 吞吐或长期内存验收。日志限制对照当前设备 init 与 [OpenWrt logd 源码](https://github.com/openwrt/ubox/blob/master/log/syslog.c)；zram 机制参考 [Linux 官方说明](https://docs.kernel.org/admin-guide/blockdev/zram.html)。
